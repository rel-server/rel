TypeScript client¶

GET /rel/database.ts serves a single, self-sufficient TypeScript file, generated fresh from your live schema. Drop it into your project and import it — there's no build-time codegen step to wire in, no ORM, and no .save(). It knows every table, column, function, and relationship your database already has, and gives you typed query building over exactly the JSON shape described in The query language.

Fetching it¶

curl http://localhost:8080/rel/database.ts?schemas=hotel > src/database.ts

schemas restricts which schemas get included — omit it and every schema but pg_catalog is exported. The endpoint is off by default outside of dev mode; see Configuration reference for http.typescript.enable and http.typescript.schemas. If you'd rather have your editor/LSP watch a real file on disk instead of re-curling by hand, typescript.helper_path has rel write database.ts straight to a path of your choosing, on startup and on every schema reload.

By default the file has no imports and depends on nothing else in your project — copy it in, commit it if you like, and it just works. codec picks other codecs (CBOR, Date or Temporal for dates and times, exact 8-byte integers) and the file then imports the one package each needs:

curl 'http://localhost:8080/rel/database.ts?schemas=hotel&codec=cbor,temporal' > src/database.ts

http.typescript.codec sets the same list for every output (the endpoint, typescript.helper_path and --typescript-out); the codec param replaces it for one request, and so does --typescript-codec for --typescript-out.

Where the server is¶

A query sends its request to /rel on the page's own origin. Outside a browser, or when the server lives elsewhere, set baseUrl (default "/"; a trailing slash is ignored). It is a property on Querier's prototype, read each time a request is sent, so it can be set for every query or for one:

import { Querier, relation } from "./database"

Querier.prototype.baseUrl = "https://rel.example.com" // every query that doesn't set its own

const other = relation("hotel.properties")
other.baseUrl = "https://other.example.com" // just this one: two servers side by side

A browser calling a server on another origin needs that server to allow it (CORS); requests are sent with credentials: "include".

Building a query¶

database.ts exports relation(), func(), and wellknown() — thin builders that return a Querier, typed against your actual schema:

import { relation } from "./database"

const properties = await relation("hotel.properties", (join) => ({
  where: [">=", ["col", "star_rating"], 4],
  join: {
    rooms: join("hotel.rooms*id:property_id", {
      select: ["*"],
    }),
  },
  select: { id: ["col", "id"], name: ["col", "name"], star_rating: ["col", "star_rating"], rooms: [".", "rooms"] },
})).get()

properties comes back typed as an array of exactly the shape you asked for — id: number, name: string, rooms: Table__Hotel__Rooms[] — not any. Get a column name wrong, or select a joined alias that isn't declared, and it's a compile error, not a runtime surprise. The same goes for relation()/func()'s own first argument: relation("hotel.bogus", ...) is a compile error too, with your editor autocompleting the relation/function names your schema actually has.

Hovering over properties (or any .get()/.write()/call() result) shows a plain, flattened object literal — { id: number; name: string; rooms: {...}[] } — at every nesting level, not the chain of internal type names that computed it.

A joined column's shortcut type-checks correctly even without a callback — write it as a plain object literal, with shortcut right on the join entry, and it's still checked against exactly the foreign keys reachable from the relation you're joining from, with autocomplete listing the valid shortcuts there:

const properties = await relation("hotel.properties", {
  join: {
    rooms: { shortcut: "hotel.rooms*id:property_id", select: ["*"] },
  },
}).get()

The scoping recurses the same way a nested join does through the callback form, below: a join nested inside a join entry is checked against its own target relation, not the root's, so the same type-checking applies at every depth without repeating a relation name anywhere:

const properties = await relation("hotel.properties", {
  join: {
    rooms: {
      shortcut: "hotel.rooms*id:property_id",
      join: {
        room_type: { shortcut: "hotel.room_types>id:room_type_id" },
      },
    },
  },
}).get()

One thing the plain-object form doesn't give you: a proto (see below) on a nested join entry written this way doesn't get its methods' this typed against that entry's own row shape — use join()'s callback form for a nested join that needs a typed proto. A wrong shortcut a few levels deep also reports the error against the enclosing join key rather than the exact line, since that's how TypeScript locates errors inside a plain object literal.

A foreign key whose referencing columns aren't indexed can't be joined, from either side (the query engine rejects it). Such a shortcut is a type error that says why, instead of being absent from the suggestions:

Argument of type '"hotel.room_types>id:room_type_id"' is not assignable to parameter of type
'"hotel.room_types>id:room_type_id" & { error: "hotel.rooms (room_type_id) has no index, so
hotel.rooms and hotel.room_types can't be joined: add an index on those columns" }'

relation()'s second argument can also be a callback, which is what you need for a nested join's proto, or when the alias/shortcut needs to be computed rather than written as a literal. The callback's join is scoped the same way: it only offers the foreign keys reachable from the relation it's called from, and the scoping recurses into nested joins automatically:

const properties = await relation("hotel.properties", (join) => ({
  join: {
    rooms: join("hotel.rooms*id:property_id", (join) => ({
      join: {
        room_type: join("hotel.room_types>id:room_type_id"),
      },
    })),
  },
})).get()

If you've already built a relation()/func() Querier for something you also want to embed as a join elsewhere, you can pass it straight to join() instead of retyping its select/proto:

const roomWithFeatures = relation("hotel.rooms", {
  select: { id: ["col", "id"], room_number: ["col", "room_number"], features: ["col", "features"] },
})

const properties = await relation("hotel.properties", (join) => ({
  join: {
    rooms: join("hotel.rooms*id:property_id", roomWithFeatures),
  },
})).get()

join() still works out on/schema/relation from the shortcut regardless — a root Querier never carries those — it just reuses everything else from the Querier you pass in.

The second argument is also optional entirely: relation("hotel.properties") alone, with no query, is a bare select-all (own columns plus every joined relation, the same default an omitted select already has server-side).

Writing back uses the same Querier, with .write() instead of .get():

await relation("hotel.properties", {
  select: { id: ["col", "id"], name: ["col", "name"] },
}).write({ id: 1, name: "Marina Bay Grand Hotel" })

write()'s argument type is derived independently from .get()'s return type, because they can genuinely differ — a column marked get in your select is read-only and drops out of the write type entirely; one marked set is the opposite, accepted on write but never returned on read. See The query language ## Selecting fields.

Only a column with no other way to end up with a value — not nullable, no default, not an identity/generated column — is mandatory in that write type; everything else (a nullable column, one with a default, an identity column) is optional, so inserting a new row only requires typing out the columns that actually need it. This follows a column through a select map's own rename too: select: { display_name: ["col", "name"] } still requires display_name if name itself is required.

wellknown() builds a call to a registered well-known query instead of an ad hoc relation — same Querier, but its params and result shape come from the query's own registered definition rather than from what you pass to relation().

Naming a row's type¶

To name the type of a row — say, as a function parameter's type elsewhere in your code — every Querier carries two type-only properties, read with typeof:

Property One row of...
typeof query.$row what .get() returns
typeof query.$draft a draft: what .write() accepts, plus the proto members

Both are a single row, not an array: .get() returns (typeof query.$row)[]. A row is assignable to a draft, so a function that edits rows can take a draft and be handed a fetched row.

import { relation } from "./database"

const properties = relation("hotel.properties", {
  select: { id: ["col", "id"], name: ["col", "name"] },
})

type Property = typeof properties.$row // { id: number; name: string }
type PropertyDraft = typeof properties.$draft

function printProperty(p: Property) {
  console.log(p.name)
}

const all: Property[] = await properties.get()

$row and $draft only exist for typeof: they are declared, never assigned, so reading properties.$row at runtime gives undefined. They are flattened the same way .get() and .write() are, so hovering Property shows the actual object shape.

A row that sits in a join is reached by indexing the root's type with the join's name. A to-many join is an array, so index it with [number]; a to-one join that can be null needs NonNullable around the indexed type:

// for a query that joins "rooms" (to-many) and "chain" (to-one, nullable)
type Room = (typeof properties.$row)["rooms"][number]
type RoomDraft = (typeof properties.$draft)["rooms"][number]
type Chain = NonNullable<(typeof properties.$row)["chain"]>

Attaching behavior to rows¶

relation()/func()/join() all accept a proto field alongside select/join/where: a map of getters, setters, methods, and property descriptors, typed against exactly the row shape that node produces. Once a node's rows come back, proto is turned into a real prototype object (once per query node, reused across every row it returns) and every row is given that prototype — its members appear on each row without being copied into the row's own JSON data:

const properties = await relation("hotel.properties", {
  proto: {
    get is_luxury(): boolean {
      return (this.star_rating ?? 0) >= 4
    },
    describe(): string {
      return `${this.name} (${this.star_rating ?? "unrated"})`
    },
  },
}).get()

properties[0].is_luxury // boolean, computed client-side, no extra column selected
properties[0].describe() // ordinary method, same `this`

Annotate the return type on every getter/method whenever proto mixes the two (a get alongside a plain method, as above) — TypeScript's inference of this inside a mixed object literal like this only works when every member's return type is explicit. A proto made up entirely of getters, or entirely of plain methods, doesn't need the annotations, but mixing without them silently degrades this to any throughout the whole object.

this inside proto is typed as the row's own computed shape — including any joined relation's own proto, so a parent's proto can read a nested join's decorated members too:

const properties = await relation("hotel.properties", (join) => ({
  join: {
    rooms: join("hotel.rooms*id:property_id", {
      proto: {
        get label() {
          return `Room ${this.room_number}`
        },
      },
    }),
  },
  proto: {
    get room_count() {
      return this.rooms.length
    },
  },
})).get()

properties[0].rooms[0].label // uses the join's own `proto`

proto's members are not part of what .write() accepts or what you pass to draft() (below): a member is not a column, and nothing says which column a setter writes. The row draft() returns does carry them, a get-only one read-only and a get/set pair assignable, the same as on a row you .get().

A proto entry can also be a property descriptor ({get, set, enumerable}), not just a plain getter/method written inline — this is what lets a reusable helper compose accessors into proto via object spread. database.ts ships one such helper per typed wire value worth converting client-side (the date and time ones only with a date or temporal codec); see that section for the full list. Spreading one in adds its member alongside anything else in proto:

const properties = await relation("hotel.properties", {
  proto: {
    ...timestampTzAccessor("created_at"),
    describe(): string {
      return `${this.name} (${this.id})`
    },
  },
}).get()

properties[0].created_at            // Timestamptz — the raw column, untouched
properties[0].created_at_as_date    // Temporal.Instant with the `temporal` codec (a Date with `date`) — derived, not stored
properties[0].created_at_as_date = Temporal.Now.instant() // writable, if the helper defines a setter

A helper's own suffix (_as_date, _as_bigint, _as_range, ...) says what it converts to, and whether the resulting member is writable depends on whether the helper defines a setter — a range accessor, for instance, is read-only.

Where-driven writes¶

A query with write_mode: "update" takes a single patch object instead of an array of rows, typed as a partial of the row; one with write_mode: "delete" takes no argument at all:

await relation("hotel.room_types", {
  write_mode: "update",
  where: ["=", ["col", "property_id"], 1],
}).write({ base_price: "99.00" })

await relation("hotel.room_types", {
  write_mode: "delete",
  where: ["=", ["col", "id"], 42],
}).write()

See Writing data back.

Building a new row¶

A row you are still working on — not saved yet, or edited and not yet written back — is a draft. A Querier's .draft() method doesn't build or create anything itself — it typechecks a row you already built against this query's own write shape (every required column, and every join, present) and attaches the same proto accessors a row you .get() would have:

const properties = relation("hotel.properties", {
  proto: {
    ...timestampTzAccessor("created_at"),
  },
  join: {
    rooms: join("hotel.properties", "hotel.rooms*id:property_id", { select: ["*~"] }),
  },
})

const row = properties.draft({
  name: "Marina Bay Grand Hotel",
  rooms: [{ room_number: "101", room_type_id: roomTypeId }], // this join is to-many, so an array
})

// The returned row has the same accessors as one you fetched. Assigning goes through the setter, which
// writes the underlying column (`created_at`), so this is how a value gets set through an accessor.
row.created_at_as_date = Temporal.Now.instant()

await properties.write([row])

A to-many join's value must be an array ; a to-one join's must be a single nested row, itself matching that relation's own write shape — draft() checks this the same way it checks the root row, it just doesn't build any of it for you. .write() still expects an array of rows at the root, same as always ; .draft() takes and returns ONE row, so wrap it in [...] yourself, the same way you would a row you built entirely by hand.

.draft() keeps what you actually passed. A column that is optional in the write shape (nullable, defaulted) stays optional on the returned row if you left it out, and becomes required if you supplied it:

const bare = properties.draft({ name: "Marina Bay Grand Hotel", rooms: [] })
bare.star_rating // number | null | undefined — optional

const rated = properties.draft({ name: "Marina Bay Grand Hotel", star_rating: 5, rooms: [] })
rated.star_rating // number | null — required, still the column's own type (not the literal `5`)
  • Joined rows are handled the same way: a to-one object, and each element of a to-many array. In an array, a key counts as supplied only if every element supplies it. An empty array supplies nothing, so its elements keep their write shape.
  • A proto accessor key (such as created_at_as_date) is not accepted in data: a key in the object would shadow the accessor, so its setter would never run, and the key would be sent to the server as an unknown field. Assign through the accessor on the returned row instead.
  • On a nested row reached through an incoming join (< or * shortcut), the column that join fills (rooms[].property_id under properties) is optional: the server writes the parent's key into it. The same relation written as the root still requires it.
  • The same goes for the referencing columns of a row's own outgoing (> shortcut) joins when the join is part of the row: rooms[].property_id may be left out if property is given, because the server writes the referenced row first and uses its key. Without the join in the shape, the column stays required. A select map that lists joins one by one keeps those columns required.
  • A key set to undefined counts as not supplied. null is a real value and counts as supplied.
  • A key the write shape doesn't have is a type error, at the root and inside joins: nmae: "x" is flagged on that key.
  • If one key has the wrong type, only that key is flagged; the other keys you supplied still count as supplied on the result.

Building a nested row¶

.draftNested(path, data) builds a draft for a row that sits inside the query's join tree, without building its parent. path lists the join names leading to it:

const room = properties.draftNested(["rooms"], {
  room_number: "101",
  room_type_id: roomTypeId, // no property_id: the parent supplies it
})

const parent = properties.draft({ name: "Marina Bay Grand Hotel", rooms: [] })
parent.rooms.push(room)
await properties.write([parent])

A deeper join is a longer path: draftNested(["rooms", "room_type"], {...}). Only join names are accepted in path, not column names, and a name that is not a join of that level is a type error.

  • data is checked against the nested row's own write shape, with the same rules as .draft(): the column the join fills in is optional, every other required column must be present, and unknown keys are rejected.
  • The result carries the proto of the join it addresses, and has the same type as (typeof properties.$draft)["rooms"][number].
  • It returns ONE row whatever the join's cardinality, never an array and never null; you put it in the array or object slot yourself.
  • It is not a query: there is no .get() or .write() for it. A nested draft is written through its parent, as above.
  • A nested draft, or a row you fetched with .get(), goes into its parent's array after the parent exists (parent.rooms.push(room) or parent.rooms = fetchedRooms), not inside the parent's .draft({...}) literal: that literal can't carry proto members.

Typed wire values¶

Every column comes back typed as the JS type its wire value actually has, not the type its Postgres type name might suggest. (int8 and numeric are the exception that proves the rule: they are bare JSON numbers, and Codecs says how to type and read them.) A timestamptz column doesn't come back as number or Date; it comes back as a distinct branded string type (Timestamptz), because the value on the wire is a string, and giving it a Date-shaped type would let you call .getFullYear() on something that has no such method at runtime. This applies to every Postgres type this section covers.

The branded types (defined once in database.ts and referenced by every column of that type):

Postgres type TS type Notes
date, time, timetz, timestamp, timestamptz PgDate, PgTime, PgTimetz, Timestamp, Timestamptz see below for accessors
interval Interval see below
money Money wire value is a locale-formatted, quoted string ("$10.50")
int4range, int8range, numrange, daterange, tsrange, tstzrange Int4Range, Int8Range, NumRange, DateRange, TsRange, TstzRange see below
the same six, as multiranges Int4MultiRange, Int8MultiRange, NumMultiRange, DateMultiRange, TsMultiRange, TstzMultiRange
inet, cidr, macaddr, macaddr8, bit, varbit, point, line, lseg, box, path, polygon, circle, tsvector, tsquery, xml, pg_lsn Inet, Cidr, MacAddr, MacAddr8, PgBit, PgVarbit, PgPoint, PgLine, PgLseg, PgBox, PgPath, PgPolygon, PgCircle, TsVector, TsQuery, Xml, PgLsn branded strings, no richer conversion (except point, below)

A branded type has no runtime representation — the value is a plain string, and the brand only makes one Postgres type's string distinguishable from another's at compile time. Passing a Timestamp-branded string where a Timestamptz is expected, for instance, is a compile error, even though both are strings at runtime.

An array of any branded type (Timestamptz[], Int4Range[], ...) needs no special handling — the wire format is a plain JSON array of the same per-element string format.

Reading a richer value¶

A branded type's own accessor helper (imported from database.ts, spread into proto) converts it into a genuinely richer client-side value. The date and time helpers exist only when the file was generated with a date or temporal codec; the examples below use temporal:

import { relation } from "./database"
import { timestampTzAccessor, int8Accessor, tstzRangeAccessor, pointAccessor } from "./database"

const properties = await relation("hotel.properties", {
  proto: {
    ...timestampTzAccessor("created_at"), // created_at_as_date : Temporal.Instant
  },
}).get()
Source type Accessor Result
Timestamptz timestampTzAccessor (date, temporal) Temporal.Instant, or a Date with date
Timestamp timestampAccessor (date, temporal) Temporal.PlainDateTime (naive — no time zone assumed), or a Date with date (a wall clock is read as UTC)
PgDate dateAccessor (temporal) Temporal.PlainDate
Interval intervalAccessor (temporal) Temporal.Duration
Int8 int8Accessor bigint, via BigInt() — exact if the value you hold is exact (see Codecs)
Int4Range/Int8Range/NumRange/DateRange/TsRange/TstzRange int4RangeAccessor/... (the date and time ones with temporal) Range<T> (below), T matching the table above
PgPoint pointAccessor {x: number, y: number}
Money moneyAccessor bigint (whole cents), via ..._as_cents
bytea (Bytea, a bare string of hex unless a codec says otherwise) bytesAccessor Uint8Array, via ..._as_bytes

moneyAccessor parses whatever currency symbol and grouping character your server's locale formats money with (confirmed against a live Postgres instance to always use 2 fractional digits) and throws if the value doesn't match — the same discipline intervalAccessor uses for a non-default IntervalStyle. Writing a ..._as_cents value back produces a plain, unformatted decimal string, which Postgres's own money input parser accepts regardless of locale.

PgTimetz and numeric have no accessor: Temporal has no "time of day with a UTC offset, no date" class for the former, and no native JS type represents an arbitrary-scale decimal for the latter. compareNumeric (also exported from database.ts) compares two PgNumeric values digit by digit, whatever type your codec gives them.

With the temporal codec the accessors return Temporal values — Temporal's classes are immutable and genuinely distinct from one another (a Temporal.PlainDateTime cannot satisfy a Temporal.Instant-typed parameter, cast or no cast), which Date alone can't offer, and Temporal.PlainDate holds a calendar day that no Date can. The file then references Temporal as a global — until it ships natively everywhere, your own project is responsible for installing a polyfill (@js-temporal/polyfill) if your target runtime doesn't have it yet. Without temporal the file references no Temporal type at all.

Writing one back¶

Each branded type with a meaningful validity check has a matching as<Type> cast (asTimestamptz, asInt8, asInterval, ...), also exported from database.ts:

import { asTimestamptz } from "./database"

await relation("hotel.properties", { select: { id: ["col", "id"], created_at: ["col", "created_at"] } }).write({
  id: 1,
  created_at: asTimestamptz(new Date()), // with the `date` or `temporal` codec ; `temporal` also takes a Temporal.Instant, any one a string with an offset
})

asTimestamptz throws if given a string with no time zone offset — Postgres would otherwise silently reinterpret it using the session's own time zone. asMoney and every range cast only brand the value, since nothing about their string shape is unsafe to skip validating. asInt8 and asNumeric only brand a value that already has the type the codec gives it.

Ranges¶

Range<T>, one immutable class shared by every range type (Range<number> for Int4Range, Range<bigint> for Int8Range, Range<string> (the decimal text) for NumRange, Range<Temporal.Instant> for TstzRange, and so on):

range.lower           // T | null — null means unbounded
range.upper           // T | null
range.lowerInclusive  // boolean
range.upperInclusive  // boolean
range.isEmpty         // boolean
range.contains(value) // boolean
range.overlaps(other) // boolean
range.equals(other)   // boolean

MultiRange<T> wraps zero or more Range<T> segments (multirange.ranges) and supports contains(value) the same way, checking every segment.

Intervals¶

intervalAccessor returns a Temporal.Duration, the natural counterpart for a span rather than a point in time. It assumes the session's IntervalStyle is postgres (Postgres's own default) and throws on a string in a different style. asInterval brands a string; the accessor's setter also takes a Temporal.Duration, serialized via its own ISO 8601 .toString() (e.g. "P1DT2H3M4S"), which Postgres's interval parser accepts regardless of the session's output-side IntervalStyle.

Table-local id types¶

A column Postgres fills in from a sequence (serial, bigserial, smallserial, or GENERATED ... AS IDENTITY) gets its own type, so an id from one table can't be passed where another table's id is expected. Every foreign key column that references one gets the same type as the column it references: a composite key is matched column by column, and a chain of foreign keys is followed to its end.

import type { Id } from "./database"

type PropertyId = Id["hotel.properties.id"] // number & { readonly __id: "hotel.properties.id" }

const room = (await rooms.get())[0]
room.property_id // PropertyId: it references hotel.properties (id)

const n: number = room.property_id // fine: an id is still a number
const bad: PropertyId = 1 as number // error: a plain number is not an id
const wrong: Id["hotel.room_types.id"] = room.property_id // error: another table's id
const literal = 1 as PropertyId // a literal id is cast explicitly
  • Id is keyed by the column's raw schema.table.column, so typing Id[" suggests every id in the schema.
  • An id converts to its bare type (number, or Int8 for a bigserial), never the other way round.
  • A foreign key whose type differs from the column it references (an int pointing at a bigserial) stays a plain type, since the wire values aren't the same kind.
  • A column that is both serial and a foreign key keeps its own type.
  • A view column that is an unmodified pass-through of an id column (select id, select e.id as entry_id ... join ..., or a view over such a view) has the same id type. An expression (id + 0, id::bigint) is a plain number again. Postgres itself says which table column each view column comes from, so no SQL is parsed.
  • Function arguments and function results keep the plain number/Int8: they accept an id but don't produce one.
  • Nothing changes at runtime. The id type only exists in the type checker, so 1 as PropertyId is free.

Calling a function directly¶

func() builds a Querier you can still shape with select/join/where, the same as relation(). When you just want to call a function and get its result back — no select, no join — use call() instead:

import { call } from "./database"

const properties = await call("hotel.rooms_available", { property_id: 1 })

call() takes the function's arguments — either the named object shown above or the equivalent positional tuple (call("hotel.rooms_available", [1])) — checked against exactly what the function declares, and resolves directly to a Promise of its return value: an array of rows for a set-returning function, a bare scalar for a scalar one. There's no Querier to hold onto and no .get()/.write() step.

Arguments are checked field-for-field against the function's own signature, so a wrong argument name or type is a compile error. A trailing argument with a database-side default is optional, the same way an optional column is on write. If a function is overloaded (declared more than once with different argument lists), the arguments you pass pick which overload's return type you get back.

func()'s own arguments field is checked the same way, with one difference: each argument may also be a ["$param", name] placeholder, since a func() query is built once and can be reused with different .get(params)/.write(params, data) values, unlike call(), which runs immediately.

Codecs¶

Three independent choices decide how values travel and what they are on the client. They are given as a comma-separated list of tokens, in any order, in GET /rel/database.ts?codec=…, in http.typescript.codec and in --typescript-codec (see Fetching it):

Choice Token What it is
Wire format json (default) JSON text, the browser's JSON.
cbor CBOR both ways, with cbor-x (bun add cbor-x). bytea is a Uint8Array, and bigint and a time type (date unless you give one) are implied.
Dates and times none (default) Text, as JSON carries them: Timestamptz, Timestamp and PgDate are branded strings, and there are no date accessors. Nothing needs Temporal.
date A timestamptz or timestamp is a JS Date (milliseconds: the microseconds of a timestamp are lost). A date stays the YYYY-MM-DD text, since a Date holds no calendar day without a time zone nor every year a date does (5874897-12-31, 0044-03-15 BC).
temporal Temporal.Instant for timestamptz and timestamp, Temporal.PlainDate for date, and the accessors for interval and the date and time ranges. Needs a runtime with Temporal, or a polyfill loaded before the first query.
Big integers none (default) Int8 is a number: JSON.parse silently rounds anything beyond 2^53.
bigint Int8 is number \| bigint: a safe integer is a number, a larger one a bigint, and a bigint can be sent. Over JSON it needs lossless-json (bun add lossless-json), which parses slower than JSON.parse: for large responses prefer cbor.

json,temporal,bigint and cbor,temporal are valid; json,cbor, date,temporal, a token twice and an unknown token are a 400 (a bad http.typescript.codec stops rel at startup). The generated file's header says which options built it (// Codec: cbor,temporal,bigint), and it has no import except for the package the options need, at its top.

The types follow the options: Int8, Timestamptz, Timestamp, PgDate and Bytea are what the codec hands over, in reads and writes, and an id column over a bigserial follows. The file offers no supported way to change them from your own code: ask for another codec instead.

What cbor gives a value (it keeps its column type instead of becoming a string):

Postgres type JS value
timestamptz Date or Temporal.Instant
timestamp Date or Temporal.Instant: the server answers the instant the wall clock stands for in its own session time zone, which the client cannot see. A column that holds another zone's wall clock reads as the wrong instant
date text, or Temporal.PlainDate
bytea Uint8Array
uuid string (hyphenated)
int2, int4, int8 number; a value of 2^32 or more is a bigint (cbor-x reads every 8-byte integer that way), so int8 is number \| bigint. Over JSON with bigint the line sits at 2^53 instead
numeric number: cbor-x reads tag 4 as Number(mantissa + "e" + exponent), so the digits beyond what a double holds (about 15 to 17) are rounded and the display scale is lost (1.50 reads 1.5), as with JSON. NaN and the infinities are floats and read as such
interval, ranges, inet, money... the same string as JSON

A JSON codec reads every number the same way, whatever column it came from, so it cannot make numeric exact without changing the type of every int4 and float8 too. When a decimal must stay exact, ask for it as text in the query — ["::", ["col", "base_price"], "text"] — and read it as a string.

Without bigint or cbor, passing a bigint in a query or a payload throws a TypeError, since the browser's JSON.stringify cannot write one.

Changing how a value is read or written¶

Every query writes its request and reads its response through Querier.prototype.codec; assign it once, or per query like baseUrl (a per-query codec must yield the same kinds of value the generated types say):

Querier.prototype.codec = myCodec

const ledger = relation("hotel.ledgers")
ledger.codec = myCodec   // only this query

A codec is an object of this shape:

interface Codec {
  contentType?: string                              // sent as Content-Type and Accept ; left out, neither is sent
  accept?: string                                   // sent as Accept instead of contentType
  binary?: boolean                                  // decode() takes the response bytes, not its text
  encode(value: unknown, options?: { structures?: boolean }): string | Uint8Array
  decode(body: string | Uint8Array): unknown
}

A failed request (status 400 or more) is always JSON text, whatever was asked, and never reaches decode: it becomes a RelRequestError whose body is that text.

Two tables are exported for finer changes, and are read each time they are used:

  • pgWireCasts holds one function per type whose written form depends on the codec (timestamptz, timestamp, date, bytea): the as… casts (asTimestamptz, …) call them.
  • With cbor, cborTags maps a CBOR tag number to {Class, encode, decode} (1 and 100 for dates and times, 37 for a uuid). Replacing an entry changes what that tag becomes; defineCborTag(tag, entry) registers a new one with cbor-x, whose tag registry is shared by the whole program.

The accessors (timestampTzAccessor, timestampAccessor, dateAccessor, bytesAccessor, int8Accessor) accept whichever form the column has: over JSON they convert a string, over CBOR they pass the value the tag decoded through. With cbor,temporal, timestamp is an instant, so there is no wall clock to read and timestampAccessor's getter gives that Instant.

Structures¶

With cbor, objects that share their keys are written once and then referred to, in both directions (the wire format): about half the bytes for rows, and decoding about three times faster in cbor-x.

  • Responses ask for them through the codec's accept, application/cbor; structures=1; assign Querier.prototype.codec.accept = "application/cbor" to have plain maps instead. cbor-x reads a layout fastest by compiling a reader for it with new Function. Under a Content-Security-Policy without 'unsafe-eval' (or in a runtime that forbids it) it tries once when it loads, catches the refusal and reads structures without compiling them, which is still about 2.7 times faster than maps (measured in Node with --disallow-code-generation-from-strings). The one attempt is still reported to the policy as a violation (a console error, and a report if the policy has a report-uri). To avoid it, make your bundler resolve cbor-x to cbor-x/index-no-eval, the build that never tries.
  • Requests use them unless sendStructures is false. It is a property of Querier, like baseUrl and codec: Querier.prototype.sendStructures = false for every query, or myQuery.sendStructures = false for one (a query built from it, with join() and the like, starts from the prototype's value again). Objects that never share their keys, such as a jsonb value used as a dictionary of ids, gain no bytes from them and take about 2.4 times as long to encode : turn it off for a query that sends mostly those. Everything else is written correctly either way.

Sharing a prototype (draft() rows, or a class) does not speed up the encoding : cbor-x compares the keys of every object whatever its prototype, and an object with a prototype of its own takes a slower path through its extensions.

The cbor code is about 100 lines: the tag entries, the encoder options, and a rewrite of what cbor-x writes differently from JSON.stringify (an undefined object member is dropped, and a whole number of 2^32 or more is sent as an integer, which an int8 column needs). Decoding is not faster with date than with temporal: building the Temporal objects is a small part of the cost, cbor-x itself the rest.

database.json¶

GET /rel/database.json serves the same introspected schema as plain JSON instead of TypeScript types — for a non-TypeScript consumer, or for tooling built directly on the raw introspected facts. See database.json.

Keeping it in sync¶

database.ts/database.json are a snapshot of the schema at the moment you fetched them — rel doesn't push updates to a client that already downloaded the file. If you add a column, add a table, or change a relationship, re-fetch to pick it up; until you do, the old file just describes the schema as it was, and a query against a field that no longer exists fails at the server, not at compile time. If you're actively iterating on the schema, typescript.helper_path (above) is the more convenient loop, since it rewrites the file on your behalf every time the schema reloads — you still have to let your editor pick up the change, but there's no manual re-fetch step.
